# Outlook read-only calendar

The installation operator supplies a public Microsoft application ID and tenant in Agenda. Coxinha does not create registrations, change consent, reuse another application's grants, or embed a client secret. No connection occurs until Connect is clicked. A browser-only preview cannot authorize Outlook.

Register the operator-owned application as a mobile/desktop public client with the loopback redirect `http://localhost/callback` (dynamic port). Authorization uses code flow with S256 PKCE and one-time state. The listener binds only IPv4 loopback, checks Host/path/state, expires after three minutes and is cancelled explicitly. ID tokens are never consumed or trusted; Graph OIDC userinfo supplies the authenticated subject. Minimal delegated scopes: `Calendars.ReadBasic openid offline_access`. ReadBasic includes invitee metadata and excludes body, attachments and extensions. No write scope is requested.

Linux uses the Secret Service OS credential store with encrypted DBus transport, Windows uses Credential Manager via keyring 3.6 (MIT or Apache-2.0). PKCE uses sha2 0.10 and base64 0.22 (both MIT or Apache-2.0). Credential entries are scoped by a hash of the installation application-data path, and refresh must preserve the authenticated subject. Missing/locked stores fail closed; tokens never enter frontend storage or calendar cache. Credentials use a versioned UTF-8 binary secret. Legacy Linux UTF-8 and Windows UTF-16 credentials are validated and migrated on successful synchronization. Windows Credential Manager permits at most 2,560 bytes, including JSON client/tenant/subject metadata and version prefix. Larger credentials fail explicitly before writing, without truncation, overwriting the previous entry or plaintext fallback. This remains a live Windows acceptance limit; support is not promised for every token size. OS-store operations run on blocking worker threads. Only public client/tenant settings are stored in frontend localStorage. The private application-data calendar cache contains invitees and event titles; it must be treated as private local data. Disconnect removes the local credentials and cache; it does not revoke tenant grants.

Sync reads a UTC calendarView from yesterday through 30 days ahead, expanding recurring occurrences, preserving immutable event IDs within the authenticated subject, organizer, series master ID, event type and original occurrence start. It rejects foreign-origin next links, redirects, repeated pages and more than 50 pages/5,000 events. A failed sync preserves the previous snapshot with its timestamp. Missing or expired credentials expose Connect again while preserving cached appointments. Missing events are never classified as cancellations. Explicit Graph cancellations remain visible.

Invitees are review candidates only. Selecting an event and an existing library meeting explicitly merges names through participantContext; the 100-candidate meeting limit is reported before writing without silent truncation; this never assigns voice identity. This increment copies candidate names explicitly; it does not persist a meeting-to-calendar-event link. No recording begins from calendar events. Future automatic recording requires a separate opt-in with device checks and duplicate/cancel handling.

Local fixture tests do not prove live authorization, enterprise consent policy, credential-store availability or Linux/Windows hardware acceptance. These gates require the operator's application and explicit live account authorization.

Primary references: [Microsoft calendarView](https://learn.microsoft.com/en-us/graph/api/calendar-list-calendarview?view=graph-rest-1.0), [permissions](https://learn.microsoft.com/en-us/graph/permissions-reference#calendarsreadbasic), [keyring 3.6 stores](https://docs.rs/keyring/3.6.3/keyring/).
